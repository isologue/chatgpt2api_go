## 场景与测量限制

- 时间：中国时间 2026-11-02，200 批次约 17:58:07 开始，500 批次约 17:59:24 开始。
- 同一台生产服务器回环地址请求 `POST /v1/images/generations`，同步、`gpt-image-2`、`n=1`、`response_format=url`，12 类正常提示词并附不同构图编号。
- 每批同时放行全部线程，不持续补充新请求；本次是突发批次测试，不是持续 200/500 QPS，也没有经过公网反向代理。因此不能证明公网入口不存在其他 502 来源。
- 压测器为 Python 线程池，每请求创建 urllib opener；该路径可能引入不必要的 TLS 上下文初始化等开销，未单独剖析验证。200 批次线程入口时间跨度 0.626s，服务端首轮尝试开始跨度 5.220s；500 批次分别为 16.543s、10.417s。
- 500 个任务确实在 Go 服务内同时处于执行状态，但实测上游生成流采样峰值为 466，不能称为已经证明 500 条上游流同时启动。
- 指标目标约每秒采样，Docker stats 约每两秒。500 批次指标采样最大间隔达到 16.424s；监控与负载线程在同一 Python 进程，存在观测停顿。峰值可能漏采，监控记录时间在发起采样前获取，不能将峰值时间精确到秒。
- Go 内部完成图片下载并完整解码后才返回成功，压测器检查 HTTP、JSON、单图数量和 URL。没有在响应之后再次下载图片，没有增加额外验图流量。
- 只有一次 200 和一次 500，账号部分已被前一批次验证，后批次可能复用验证缓存。尚未覆盖长期稳定性、全部冷缓存、异步/base64、大图不同分辨率、公共代理入口和 1000 实际上游并发。

## 阶段耗时

统计以每次账号尝试/图片阶段为单位，重试前后会分别计入，不能将各阶段 P95 直接相加作为请求 P95。

| --- | ---: | ---: |
| 上游生成流 | 22.438s | 26.381s |
| 账号校验（含该阶段等待） | 1.389s | 3.621s |
| 下载槽位等待 | 0.003ms | 7.001s |
| 图片传输 | 2.097s | 5.886s |

500 批次下载等待最长 7.501s、传输最长 6.794s；下载并发限制为 64。没有观察到工作量证明排队成为瓶颈。账号状态写入与选号等阶段外开销很小；最终日志写入最长 38ms，没有出现先前怀疑的秒级日志确认等待。

200 批次：3 次 `image_result_uncertain`；500 批次：5 次 `image_result_uncertain`、2 次 `no_image_generated`。这些中间尝试都执行了约 10s 的结果补查，再切换账号，全部恢复。SSE 阶段硬超时累计为 0，没有触发硬超时总预算豁免。本次没有触发下载失败重试。

## 资源与瓶颈判断

| 资源采样峰值 | 200 请求批次 | 500 请求批次 |
| --- | ---: | ---: |
| Go 容器 CPU | 679.00% | 1061.22% |
| Go 容器内存 | 128.4MiB | 195.3MiB |
| Go heap | 73.12MiB | 102.39MiB |
| PostgreSQL CPU | 50.75% | 37.98% |
| WARP CPU | 318.95% | 373.81% |
| 主机 eth0 接收速率 | 619.26Mbps | 923.17Mbps |

服务器为 32 CPU、约 64GiB RAM。Docker 1061% 约对应 10.6 个 CPU 核心，不代表整机使用率为 1061%。本次 Go CPU、内存和 PostgreSQL 指标没有显示明显耗尽。

200 批次内部图片下载合计约 517.5MiB，500 批次约 1297.3MiB。随着负载提高，500 批次下载槽位打满、队列形成，单张图片传输时间也变长，说明集中回图阶段值得优先分析。主机网卡接收峰值约 923Mbps 已接近千兆量级，但包含其他服务、代理协议及其他流量；没有取得线路实际限速或隔离对照，不能据此断定带宽就是唯一瓶颈。

上游生成仍占主要耗时，少量补查与切号决定长尾。未观察到之前那类几十秒的内部阶段外空档；这只适用于本次 Go 原型、账号集合与服务端路径，不能与旧版本历史批次直接作同条件性能对比。

建议下一步先修正压测器：复用轻量 HTTP 连接配置，将准备工作放在放行之前；将监控独立为进程，记录实际发出请求和采样完成时间。然后在其他参数固定时，按 64→96→128 的下载并发对照测试，比较有效下载吞吐、等待、传输、错误率和 WARP/网卡负载；只有吞吐继续提升时才调高默认值。本轮没有盲目修改下载并发，也没有再消耗一轮真实图片额度。
