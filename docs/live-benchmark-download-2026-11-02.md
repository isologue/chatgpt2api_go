# Go 原型下载与解码对照压测（2026-11-02）

本轮完成 5 组真实上游 500 并发单批测试，共 2500 个请求。2496 成功、4 个最终 `504 image_result_uncertain`，成功率 99.84%；没有空体 502，也没有下载失败。确认了一个本地瓶颈：下载并发提高后，完整图片解码队列会成为等待点。解码从 4 提到 8 明显减少这部分等待，但本轮整体 P95 没有改善，不能据此宣称全链路提速。

所有时间使用北京时间。仅修改独立 Go 测试栈，原 Python 项目的代码、Compose、容器和数据库未修改。图片由 Go 内部下载并完整解码，压测器没有再次下载图片。

## 测试方法与有效性

- 线上独立地址 `127.0.0.1:9080`，1269 个 AT-only 测试账号，复用原 WARP 出站网络。
- 使用新的 Go `cmd/burst`，所有 JSON 和请求预先构建，500 个 goroutine 就绪后同时放行。实际写出请求跨度 97～130ms；修正了前轮 Python 发包线程启动分散十余秒的问题。
- 监控运行在独立 Python 进程，复用 HTTP 连接，每 0.5s 采样，另外记录 Docker stats、主机网卡和 CPU 累计计数。最大采样间隔 0.523s，最大采样请求耗时 25.1ms，无采样失败。
- 每组从同一套测试账号缓存与评分快照恢复，重启测试 core，清零运行计数。第一轮三组共用一份快照；第二轮两组另取快照，账号缓存大多有效，不能将第二轮的账号校验耗时与第一轮直接比较。
- 两个对照阶段都固定 12 种提示词及请求序号，保持 workers=1000、queue=1000、账号槽位=1、verify=50、DB connections=32、total=120s、SSE=80s、poll=10s、download timeout=15s、switch retries=2、download retries=1。
- 本地数据库快照无法重置上游真实额度、限流、会话状态与负载。测试顺序未随机化，也没有重复多轮，因果结论有限。
- 每组都是一次性放行 500 个请求，完成后结束；不是持续维持 500 并发，也不是公网调用入口测试。`sse_active` 只是上游生成流连接数，不代表上游 GPU 同时计算数量。

## 三、资源和故障归因

- 五组最终 4 个失败都在三次账号尝试后返回 `image_result_uncertain`；没有下载、完整解码或本地存储失败。其中一个先收到 `no_image_generated`，随后两次结果不确定；其他三个均连续结果不确定。对应失败请求约 52.7～55.3s，不是等待下载名额耗尽。
- 累计两次 SSE 80s 硬超时，均不属于这四个最终失败；两次所在请求最终成功。硬超时恢复计数与预算豁免逻辑仍保留。
- 五组成功图片 2496 张，全部清理，共 6,789,977,520 字节（约 6.32GiB）。失败临时文件由服务清理，收尾检查图片目录为空。没有额外验图下载，也没有图片传回本地。
- PoW 实际计算 P95 约 2～3ms，排队 P95 不超过数微秒，不是本轮瓶颈。
- 最终请求日志写入前后的耗时差 P95 为 4～7ms，最大 32ms，没有出现秒级日志确认等待。该差值还包含日志写入前后少量计数等工作。
- 第一轮 Go CPU 峰值约 1007～1042%，第二轮约 1477～1558%；峰值出现在批次开始约 2～3.5s。机器有 32 个逻辑 CPU，1558% 约为 15.6 个逻辑 CPU 的用量。不能把不同批次启动阶段的峰值差直接全部归因于解码。
- 全部测试中 WARP CPU 峰值约 413%，Go 内存峰值 230MiB，PostgreSQL CPU 峰值约 45%。未显示本机内存或数据库连接耗尽。
- 主机 eth0 半秒窗口接收峰值约 1.13～1.23Gbps，5 秒窗口峰值约 0.87～1.03Gbps。下载 96→128 时 5 秒窗口峰值仅从约 1.01 升到 1.03Gbps。数据提示集中回图期间网络路径可能接近吞吐平台，但含原项目和代理的流量，尚未取得实际线路限额或隔离对照，不能确认服务器带宽是唯一瓶颈。

## 四、本轮代码与运行状态

新增 `cmd/burst` 压测工具和真实写出时间；新增下载连接响应、响应体、解码预检、解码等待、实际解码阶段；新增 `validation_active`、`validation_waiting`、`validation_limit` 指标。测试覆盖解码排队时释放下载名额、取消清理和连接/响应体分开计时。`go test -race ./...` 与 `go vet ./...` 通过，镜像构建通过。

阶段语义发生细分：旧 `图片传输` 含连接响应，旧 `图片校验` 含排队；新版分别拆开。因此跨镜像比较必须先在逐尝试记录中合并对应阶段。

测试结束保留观测版镜像，测试栈恢复 download=64、decode=4 的基线配置；默认值没有盲目提高。decode=8 是这台 32 CPU 服务器上有局部收益的候选值，需要在上游状态更稳定、交错或重复试验下再确认整体收益。原 Python 项目未修改，当前没有合并或推送代码。

下一步优先为未出图/结果不确定保留不含凭据的上游终止原因，核对账号重复使用与额度/限流，减少无效补查与切号。网络侧需要隔离 WARP、CDN 和主机带宽的对照，暂不继续盲目提高下载并发。
